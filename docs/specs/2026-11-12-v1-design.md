# Crosscheck 第一版设计说明

- 日期：2026-11-12
- 状态：待评审
- 范围：子项目 1（内核 + AI 验收测试员），子项目 2～4 只定义接口边界

## 1. 背景与目标

越来越多的项目里，需求文档和代码都由 AI 生成。如果测试也让 AI 照着代码写，三者会“一起错、一起绿”：测试只证明了“代码是这么写的”，证明不了“代码应该这么写”。

Crosscheck 是一个通用的 AI 自动化测试 CLI，面向任意 Web 项目，目标是：

1. **判定标准独立于代码**：对错只能依据经人确认的需求条款，不能从业务代码推导。
2. **判定必须有证据**：证据由工具层自动采集，AI 的判定必须引用证据，没有证据的判定无效。
3. **交叉复核**：执行和复核分别使用不同的模型（建议不同厂商），复核方看不到执行方的结论，独立判定。
4. **人掌握裁决权**：需求条款、用例、争议结果都由人在 TUI 中确认；AI 只负责提炼、执行、复核和找问题。
5. **支持任意模型**：按角色配置模型，不绑定任何厂商。

### 非目标（第一版不做）

- 移动端、桌面端、CLI 或库类项目（第一版只做 Web：浏览器 + HTTP，可选只读数据库）。
- 没有需求文档时，从代码反推“行为快照”。
- 把用例固化成 Playwright 脚本（子项目 3，本版只记录可固化的轨迹）。
- 无人值守、CI 与定时运行（子项目 4，本版只保证工件和退出码适合将来接入）。
- Web 界面版的审核平台。

## 2. 子项目拆分

| 序号 | 子项目 | 本版状态 |
|---|---|---|
| 1 | 内核 + AI 验收测试员：画像、条款、用例、执行、复核、报告、TUI 审核 | **本文档范围** |
| 2 | 项目适配增强：Spring、Express、Vue Router 等框架的探测插件 | 只定义插件接口，内置 OpenAPI 插件和录制 |
| 3 | 固化脚本：根据执行轨迹生成 Playwright 测试 | 只记录轨迹格式 |
| 4 | 无人值守：`crosscheck ci`、定时运行、结果通知 | 只约定退出码与机器可读结果 |

## 3. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript（Node.js ≥ 20，ESM） | Playwright 原生语言；npm 分发，`npx crosscheck` 即可使用 |
| 工程 | pnpm monorepo | 各包职责单一，便于后续拆分发布 |
| 模型层 | Vercel AI SDK v7（`ai` + 各 `@ai-sdk/*` provider） | 统一的多厂商接口；兼容 OpenAI 协议的服务都能接；支持多步工具调用、`Output.object` 结构化输出和 `@ai-sdk/mcp` |
| 代理循环 | 自研（基于 `generateText` 单步调用组装） | 流程需要代码硬控制：分阶段授予工具、强制证据、预算上限 |
| 浏览器 | Playwright（直接调用库，不经过 MCP） | 稳定可控；动作和定位器可以直接记录，供子项目 3 固化 |
| 结构校验 | zod | 配置、工件和模型输出共用一套 schema |
| TUI | Ink | 适合做复杂的终端交互：列表、分栏、快捷键 |
| CLI | commander | 成熟、轻量 |
| 测试 | vitest | 与 TS 生态一致 |

## 4. 包结构

```
crosscheck/
├─ packages/
│  ├─ cli          命令入口，参数解析，组装各包
│  ├─ core         工作流引擎、工件存储、确认（哈希）机制、纪律守卫、合议逻辑
│  ├─ models       按角色解析模型、重试与备用模型、token/费用统计
│  ├─ agent        代理循环：工具授予、步数/token/时长预算、上下文压缩、结构化输出校验
│  ├─ tools        代理工具：browser / http / db(只读) / fixture / profile 查询；证据采集
│  ├─ discovery    系统画像探测：插件接口、OpenAPI 插件、静态扫描、录制
│  ├─ tui          Ink 审核界面
│  ├─ report       静态 HTML 报告、results.json、JUnit XML
│  └─ codegen      （子项目 3 预留，本版只有类型定义）
└─ examples/
   └─ shop-demo    靶场：小型 Web 应用 + 需求文档 + 植入的已知 bug
```

依赖方向：`cli → (tui, report, discovery, agent) → tools → core`，`agent → models → core`。`core` 不依赖任何其他包。

## 5. 被测项目中的工件（`.crosscheck/`）

除 `runs/` 以外的所有工件都提交到被测项目的 git 仓库，审核历史可以通过 git diff 追溯。

```
.crosscheck/
├─ config.yaml           模型角色、预算、默认环境、需求文档位置
├─ system/               系统画像
│  ├─ environments.yaml  环境：基础地址、启动/停止/健康检查命令、白名单
│  ├─ auth.yaml          认证方案：各角色怎么登录（表单、token 注入、录制回放、自定义命令）
│  ├─ api-catalog.yaml   接口目录：方法、路径、参数、来源（openapi/代码/录制/运行时）
│  ├─ pages.yaml         页面地图：路由、页面说明
│  ├─ data-model.yaml    数据模型与具名只读查询
│  ├─ fixtures.yaml      场景夹具：名称、说明、实现（命令/HTTP/SQL）、参数
│  └─ guardrails.yaml    禁止操作、地址白名单、需要脱敏的字段
├─ requirements/         验收条款，每个模块一份，比如 M09.yaml
├─ cases/                用例，每个模块一份
├─ approvals.json        工件的内容哈希与确认记录
└─ runs/<时间戳>/         执行记录：轨迹、证据、判定、报告（不提交）
```

### 5.1 验收条款

```yaml
- id: M09-AC-003
  text: "“为什么是 X 票？”正确列出成员身份、各 NFT 数量 × 权重、已使用编号（置灰）"
  source: { file: doc/requirements/M09-社区投票与计票.md, line: 439, excerpt: "..." }
  status: active          # active | unclear | removed
  notes: ""
```

### 5.2 用例

```yaml
- id: M09-TC-007
  covers: [M09-AC-003]
  fixtures: [reset, member-with-2-nft, proposal-in-voting]
  actor: member            # 对应 auth.yaml 中的角色
  steps:
    - 打开投票中提案详情页
    - 点击“为什么是 X 票？”
  expectations:
    - id: E1
      text: 列出成员身份与每种 NFT 的数量 × 权重
      evidence: [screenshot, dom]      # 判定必须引用的证据类型
    - id: E2
      text: 已使用的编号置灰显示
      evidence: [screenshot, dom]
```

### 5.3 确认机制

- `approvals.json` 记录每个工件条目的规范化内容哈希、确认人、确认时间。
- 条目内容改变后哈希不再匹配，原来的确认自动失效，必须重新确认。
- 只有已确认的条款才能生成用例，只有已确认的用例才能执行。

## 6. 系统知识的来源

**原则：系统知识（怎么操作）可以来自代码和运行时；判定标准（对不对）只能来自已确认的需求条款。**

| 来源 | 内容 | 本版实现 |
|---|---|---|
| 静态扫描 | README、package.json、pom.xml、docker-compose、.env.example、启动脚本 → 环境与启动命令 | 内置通用扫描 + 由模型归纳 |
| OpenAPI | 接口目录 | 内置插件 |
| 框架插件 | 从路由代码提取接口、页面 | 只定义插件接口（子项目 2） |
| 录制 | `crosscheck record` 打开有界面的浏览器，人操作一遍，记录动作和 HAR → 学习登录流程、关键接口 | 内置 |
| 运行时积累 | 执行时观察到的接口，以“运行时”来源补充进接口目录（需确认后生效） | 内置 |
| 人工补充 | 账号、验证码规则、第三方依赖的 Mock 方式、禁止操作、夹具实现 | 在 TUI 中引导填写 |

画像按需提供给代理：代理通过 `profile.*` 工具检索，不会把全部内容塞进上下文。执行中发现画像和实际不符（比如接口 404、页面元素缺失），会记录为**画像漂移**，用例判为 `BLOCKED`，并在报告中提示更新画像。

## 7. 工作流与命令

| 命令 | 作用 | 使用的模型角色 |
|---|---|---|
| `crosscheck init` | 扫描项目，生成 `config.yaml` 和系统画像草稿 | extractor |
| `crosscheck record [--role <角色>]` | 录制人工操作，补充认证方案和接口 | extractor |
| `crosscheck reqs [--module <模块>]` | 从需求文档提炼验收条款 | extractor |
| `crosscheck plan [--module <模块>]` | 由已确认条款生成用例 | planner |
| `crosscheck review [条款\|用例\|结果]` | 打开 TUI 审核 | 无 |
| `crosscheck run [--module] [--case] [--resume]` | 执行已确认用例 → 复核 → 报告 | executor, reviewer |
| `crosscheck report <runId>` | 重新生成或打开报告 | 无 |

阶段顺序由 `core` 的工作流引擎强制：画像确认 → 条款确认 → 用例确认 → 执行。`plan` 阶段的代理**不提供读取业务代码的工具**，只能读条款和系统画像。

## 8. 单个用例的执行流程

```
预检 → 准备 → 执行 → 自判 → 盲审复核 → 合议 → 定论
```

1. **预检**：对目标环境做健康检查；校验目标地址在 `guardrails.yaml` 的白名单内，不在就拒绝执行。
2. **准备**：执行 `reset` 和用例声明的夹具。缺少夹具时进入“现场造数”子阶段：代理通过页面或接口搭建状态，结果打上 `低可靠` 标签，并生成夹具建议（需要的状态和建议的实现方式）。
3. **执行**：executor 代理按步骤操作。证据由工具层自动采集，每份证据有唯一 ID：
   - 每个浏览器动作前后的截图和可访问性快照；
   - 网络请求和响应（HAR），以及控制台错误；
   - 数据库只读查询的结果。

   同时记录可固化的轨迹，包括动作类型、定位器、输入值，供子项目 3 使用。
4. **自判**：executor 对每条预期输出 `{expectationId, verdict, evidenceIds[], reasoning}`。守卫校验：引用的证据确实存在，且类型满足预期要求的证据类型；不满足的判定作废。
5. **盲审复核**：reviewer 只拿到条款原文、用例预期和证据，**拿不到 executor 的结论和推理**，独立判定。模型不支持图片时，改用可访问性快照和 HAR 的文本形式。
6. **合议**：

| 状态 | 条件 | 去向 |
|---|---|---|
| `PASS` | 双方都判定符合 | 结束 |
| `FAIL` | 双方都判定不符合 | 报告为疑似 bug，等人确认 |
| `DISPUTED` | 双方判定不一致 | TUI 人工裁决 |
| `UNCLEAR` | 任意一方认为条款模糊或矛盾，无法判定 | 回到条款修订 |
| `BLOCKED` | 环境、夹具、画像出问题，画像漂移，预算耗尽，或输出多次校验失败 | 修复后重跑 |

附加标签：`低可靠`（现场造数，或执行中出现重试）。

用例的结果取它所有预期中最严重的状态，严重程度为：`BLOCKED` > `FAIL` > `DISPUTED` > `UNCLEAR` > `PASS`。

### 8.1 防作弊硬约束

- 工具按阶段授予：执行阶段**不提供夹具工具**，数据库工具始终只读（只允许执行画像中登记的具名查询，或经过只读校验的 SELECT）。
- HTTP 和浏览器请求受 guardrails 约束（白名单、禁止的路径和方法）。
- 代理遇到障碍只能上报 `BLOCKED`，不能绕过。
- Crosscheck 不写入被测项目的源码和测试，只写 `.crosscheck/` 目录。
- 每个用例有步数、token、时长三项预算，超出即判为 `BLOCKED`（预算耗尽）。

## 9. 模型配置

```yaml
models:
  extractor: anthropic:claude-sonnet-4-6
  planner:   deepseek:deepseek-chat
  executor:  openai:gpt-5.4
  reviewer:  qwen:qwen-max
  fallback:
    executor: anthropic:claude-sonnet-4-6
providers:
  qwen:
    type: openai-compatible
    baseURL: https://dashscope.aliyuncs.com/compatible-mode/v1
    apiKeyEnv: DASHSCOPE_API_KEY
budget:
  perCase: { steps: 60, tokens: 400000, minutes: 10 }
```

- 模型写成 `provider:model` 形式。内置 anthropic、openai、google、deepseek、ollama，其他厂商用 `openai-compatible` 接入。
- 密钥只从环境变量读取，配置中只写变量名。
- executor 和 reviewer 配成同一厂商时给出警告，但不阻止运行。
- 模型 ID 以实现时各厂商的实际可用 ID 为准，上面只是示例。

## 10. TUI 审核

- **条款视图**：逐条显示条款和来源原文。快捷键：通过 / 编辑（打开 `$EDITOR`）/ 标记待确认 / 删除 / 批量通过本模块。
- **用例视图**：按条款分组，顶部显示覆盖率，没有用例覆盖的条款高亮。操作与条款视图相同。
- **结果视图**：针对 `FAIL` 和 `DISPUTED`。左右并排显示两个模型的判定，下方列出证据，按 `o` 键用系统程序打开截图或 HAR。裁决选项：确认是 bug / 误报 / 条款有问题（回写条款状态为 `unclear`）。
- 画像审核也在 TUI 中完成，用来补充人工信息。

## 11. 报告

- `runs/<时间戳>/report/index.html`：单目录静态站点，可以直接打开。内容包括：
  - 总览：各状态计数、耗时、token 与费用；
  - 追溯矩阵：条款 × 用例 × 结果；
  - 用例详情：截图时间线、请求和响应、双方判定；
  - 夹具建议、画像漂移列表。
- `results.json`（机器可读）和 `junit.xml`。
- 预留的退出码（供子项目 4 使用）：`0` 全部通过；`1` 有 `FAIL`；`2` 有 `DISPUTED`、`UNCLEAR` 或 `BLOCKED`；`3` 工具自身出错。

## 12. 错误处理

- **模型调用**：指数退避重试；连续失败后切换到 `fallback` 配置的备用模型。结构化输出用 zod 校验，不合格时把错误反馈给模型重试，最多 3 次，仍失败判为 `BLOCKED`。
- **断点续跑**：每个用例完成后立刻落盘，`run --resume` 跳过已完成的用例。
- **故障隔离**：浏览器崩溃或超时只影响当前用例，每个用例使用独立的浏览器上下文。
- **脱敏**：证据中 `Authorization`、`Cookie`、`Set-Cookie`、密码字段，以及 `guardrails.yaml` 中登记的字段，落盘前一律脱敏。
- **中断**：按 Ctrl+C 后，当前用例记为 `BLOCKED（中断）`，然后关闭浏览器并退出。

## 13. 工具自身的测试

1. **单元测试**（vitest）：工件读写与哈希确认、工作流状态机、守卫、合议规则、脱敏、预算。
2. **假模型**：实现一个按脚本返回结果的 AI SDK provider，确定性地测试代理循环和各阶段流程，不消耗 token。
3. **靶场**（`examples/shop-demo`）：
   - 一个小型 Web 应用，包含登录、列表、下单、后台审核；
   - 对应的需求文档；
   - 若干**植入的已知 bug**，清单单独存放，工具运行时不可见。

   用真实模型跑完整流程，统计两个指标：**召回率**（找出了几个植入的 bug）和**误报率**（正常条款被判为 `FAIL` 的比例）。这是衡量 Crosscheck 质量的核心指标。
4. **真实试点**：社区治理项目（`E:\community-governance`）。它的钱包签名、Mock 链、时间快进、固定验证码，正好用来检验画像和夹具的设计。

## 14. 验收标准（第一版）

- [ ] 在靶场上，`init → reqs → review → plan → review → run` 全流程可以跑通。
- [ ] 未确认的条款或用例无法进入下一阶段；修改已确认的条目后，确认自动失效。
- [ ] 判定没有附证据或证据类型不符时作废；reviewer 的输入中不含 executor 的结论。
- [ ] 执行阶段代理无法调用夹具，也无法执行写数据库的语句（有对应的单元测试）。
- [ ] 执行和复核可以配置为不同厂商的模型，至少验证 3 家：Anthropic、OpenAI 兼容服务、Ollama 本地模型。
- [ ] 靶场召回率 ≥ 80%，误报率 ≤ 10%（以 3 次运行的平均值计）。
- [ ] 报告中包含追溯矩阵和证据，TUI 能完成三类审核与裁决。
- [ ] 社区治理项目至少一个模块（建议 M09）完成接入并跑通。
