# init 一条命令完成笔记与画像：设计

日期：2026-11-23
状态：已实现（2026-11-26）

## 目标

把原先分开的笔记生成、笔记确认、画像生成和画像审核合并到 `init`，减少人工确认的工作量。新生成的笔记由宿主自动确认；画像只对指定文件做来源核验与自动确认，其余交给人审核。

## 非目标

- 不改 `reqs → review clauses → plan → review cases → run` 的人工门禁。
- 不把画像确认改成条目级；确认记录仍绑定整份画像的内容哈希。
- 不改 `gate.ts` 的判定逻辑。
- 不移除 `profile` 命令：它仍要求笔记已确认，只生成草稿，不自动确认。

## 流程

1. 读取 `.crosscheck/config.yaml`，缺少时写入默认配置。已确认笔记默认跳过；`--refresh` 将旧笔记作为上下文，重新生成并自动确认，不保证保留人工补充。未确认或编辑后失效的笔记直接重跑会被覆盖；要保留编辑结果，可先用 `review notes` 人工确认。笔记生成的输入或结果校验失败时退出 2，不继续生成画像；生成文本无法无损编码为 UTF-8 时不写入，保留原笔记与确认。需求文档范围不可用时单独诊断，见下文。
2. 不带 `--refresh` 且笔记及七份画像均已有有效确认时，跳过 `profileCommand`，无需配置或调用模型，直接执行最终校验。其他情况复用 `profileCommand`，生成七画像中缺少有效确认的文件。`init` 与 `profile` 均接受可重复的 `--openapi <文件>`，省略时使用默认候选文件。两条命令均跳过仍有有效确认的画像，`init --refresh` 也不覆盖它们。
3. 对未确认、格式有效的 `api-catalog` 和 `pages` 逐条核验来源。至少有一条通过且没有来源读取故障时，才剔除未通过项、输出剔除信息，并整份自动确认；没有条目通过、扫描不完整、来源读取故障，或画像引用未被扫描登记的显式 `--openapi` 文件时，保留原稿并交由人审。`environments`、`auth`、`data-model`、`fixtures`、`guardrails` 始终由人确认。
4. 按文件内容与确认记录列出所有待确认画像，包括缺失、格式无效或确认失效的文件。stdin、stdout 均为 TTY 时，独立 `init` 直接打开仅列待确认画像的审核界面；非 TTY 有待确认画像时打印清单并退出 2，可另在交互终端运行 `review profile`。`/init` 在会话内交接同样范围的审核，退出审核后返回聊天。筛选只影响展示；七份画像均已确认时，审核界面对全部画像做交叉校验。两个入口的筛选界面若提示校验失败，可按 `f` 进入完整画像审核，编辑原先隐藏的已确认画像，包括 `auto` 确认的画像。
5. 独立 `init` 的人审结束后若仍有待确认画像，提示剩余项，并遵循原 `review` 退出约定（`q` 或顶层 `Esc` 正常退出为 0，`Ctrl+C` 中断为 2）。若无需人审，或人审正常结束后七画像均已确认，则重读并校验笔记的确认状态、七画像的格式与交叉引用，再以通过交叉校验的画像内容复查确认；复查发现笔记缺失、不是有效 UTF-8、笔记或画像未确认或确认失效，或发现必需画像缺失、画像结构或交叉引用不合法时，退出 2。YAML 解析异常等未归入这些检查的错误可能按宿主错误退出 3；实际宿主读取故障仍退出 3。会话内交接的审核返回聊天，不走独立命令的人审后收尾流程。

## 条目核验规则

`pages` 与 `api-catalog` 的条目带有 `sources: {file, line, excerpt}[]`。至少一个来源须满足：文件是扫描登记的项目内安全路径且可读，行号有效，脱敏后的该行包含非空摘录，或整行按与摘要一致的方式规范化后与摘录完全相等。后一规则兼容脱敏重新序列化的单行 JSON OpenAPI，不对摘录再做规范化以放宽匹配。读取复用 `createProjectReader` 和 `readCleanLines`。核验只证明行与摘录匹配，不证明接口、页面、描述或其他画像语义正确，也不授予网络或执行权限。

不存在、未登记、不安全或摘录不匹配的普通来源不能通过核验。有通过项且可以判定来源时，未通过的条目整条剔除，不修改保留条目；若没有通过项或本来就没有条目，则保留原文件，不自动确认。查询登记来源遇到读取故障时，即使其他来源通过，也保留整份画像原稿，提示排查重试或人工审核。画像若引用未登记的安全显式 `--openapi` 路径，同样保留整份原稿交人审，不因显式指定而扩大扫描登记范围。核验在本地进行，不把为此重读的来源内容发给模型。

## 确认记录

- 确认记录结构仍为 `hash`、`by`、`at`。自动确认写入保留身份 `auto`，不需要解析人工确认人。
- 交互式人工审核照常取 `CROSSCHECK_REVIEWER` 或系统用户名，拒绝使用保留身份 `auto`。历史同名记录不迁移；由于结构未变，无法与自动确认区分。
- 编辑工件使其内容哈希改变时，原确认照常失效。`review profile` 列表和 `/status` 的“已确认画像”区显示有效已确认画像的确认人。
- 人工审核写入前重载确认表，仅合并本次确认或撤销的条目；检测到同一条记录自会话打开或刷新以来、或在动作期间已变化时拒绝保存并提示重试。只编辑画像文件不重写确认表，保存编辑前会复查原文件。这不保证最后一次检查与保存之间的原子性。

## 实现位置

- `packages/cli/src/init.ts` 串联笔记、画像生成、核验、自动确认与审核；直接调用 `packages/cli/src/profile.ts` 的 `profileCommand`。
- `packages/discovery/src/verify-entry-sources.ts` 核验画像条目的来源，返回保留项及剔除原因。
- `packages/core/src/approvals/reviewer.ts` 定义 `AUTO_REVIEWER` 并保留该交互式确认人身份。
- `packages/cli/src/args.ts` 支持 `init --openapi`；`packages/cli/src/review.ts` 和 `packages/cli/src/session.ts` 将待确认画像清单传给审核视图。
- 根 README、CLI README 和手工接入指南说明新流程及边界。

## 错误与边界

- 生成、自动确认与完成检查会复查相关文件内容和确认记录，发现不一致时停止相应写入或确认，不提供原子比较并交换、跨文件快照或跨进程原子事务。
- 自动确认在对应文件成功写入（无需改写时为核验现有文件）并复查后登记。中断不回滚已完成的写入，可能留下已写入但未确认的文件；已完成的确认保留。
- 全部画像获确认不代表交叉引用有效。若 `fixtures` 的 HTTP 夹具引用了被剔除的接口条目，审核界面会提示交叉校验问题；独立 `init` 在最终复查时退出 2，需修正引用并重新确认。

## 自动确认笔记的需求文档范围

项目配置中 `requirementsDocs` 非空时始终优先；仅为空时 `reqs` 才读取已确认笔记的“需求文档”小节。显式配置与人工确认笔记沿用原有路径校验和目录展开规则。`impact` 使用同样的配置优先级，但只读分析，不要求笔记已确认，也不使用宿主登记门禁。

- `init` 生成含需求文档条目的笔记时，宿主严格展开目录，候选文件必须是本次扫描实际登记的安全路径。扫描有诊断、目录无法完整展开或候选文件未登记时提示人工处理，可继续保存并确认笔记，但不登记任何可供 `reqs` 使用的路径。宿主在签署笔记前将笔记内容哈希及核验后的路径集合写入 `.crosscheck/notes-discovery.json`；范围核验不读需求正文，记录不保存正文，也不写回 `config.yaml`。
- `reqs` 使用 `auto` 笔记时，先要求宿主记录可读且哈希与当前笔记匹配，再扫描项目并严格展开目录，要求文档路径集合与生成时登记完全一致。新增未登记文件、原候选文件移除、扫描或展开不完整、文档读取失败均阻断并退出 2，不调用需求提取模型。登记约束路径范围，不绑定文档内容哈希，也不提供跨次读取快照。
- 旧版 `auto` 笔记没有匹配记录时不会自动补齐，可用 `init --refresh` 重生成笔记与登记，或人工核对后用 `review notes` 确认，也可显式配置 `requirementsDocs`。如扫描或展开仍不完整，应改用人工确认或显式配置。

笔记自动确认不保证有人看过，只影响画像生成和需求文档范围，不直接决定测什么。条款和用例仍须人工确认，执行仍须通过原有门禁。

## 测试

- 来源核验覆盖摘录匹配（含带空格的单行 JSON OpenAPI）、文件不存在、越界行号和受限路径；无通过项、读取故障或引用未登记的显式 OpenAPI 时保留原稿、不自动确认。
- 覆盖 `api-catalog`、`pages` 的 `auto` 确认、其余画像的人审、编辑后确认失效、TTY/非 TTY 交接，以及独立与会话筛选审核中按 `f` 打开完整列表。
- 覆盖自动笔记登记及重校验、缺失或损坏的登记、扫描后新增文件、遍历诊断与读取超限；覆盖全确认且无模型配置的最终交叉校验、`--refresh` 只刷新笔记、拒绝无法无损编码的笔记、`profile` 草稿行为、条款和用例门禁，以及并发修改检测和中断。

## 与原 spec 的差异（按最终实现）

1. 不另抽生成函数：`init` 直接复用支持传入取消信号的 `profileCommand`。
2. `api-catalog` 或 `pages` 原本为空、或没有任何条目通过核验时，保留原文件交人审，不写回空画像或自动确认。
3. 历史计划曾拟略过 `/status` 的逐项确认人，最终实现同时在 `review profile` 与 `/status` 显示有效画像确认人。被剔除的接口导致交叉引用失效时，除审核界面提示外，独立 `init` 也会在最终校验时退出 2。
